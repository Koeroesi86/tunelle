# Validating data with Zod

Data that crosses a boundary is read with a Zod schema, and its type is `z.infer` of the schema.

- **Messages from the renderer:** schemas in `shared/schemas/` (`requests.ts` for the library, launcher, update, artist photo and settings messages, `playlists.ts`, `favourites.ts`), applied with `parsePayload` (`electron/utils/parse-payload.ts`). A message that does not match is dropped and the log names the fields that are wrong.
- **Table schemas (generated):** `npm run generate:schemas` applies the migrations to a database in memory and writes a schema of the rows of each table to `electron/schemas/database/` (`scripts/tooling/generate-database-schemas.ts`). The folder is not in git, and `postinstall`, `dev`, `build` and the `lint`, `fallow`, `typecheck` and `test` scripts run the generator first (npm `pre` hooks), so the schemas follow the migrations. The generated schemas say what the table holds (`TEXT` is a string, a column that is not `NOT NULL` is nullable); a schema written by hand takes one with `.pick()` or `.extend()` only for what the table does not say: a JSON column, the names the app uses, the limits of a key, a NULL read as empty text.
- **Reuse:** a schema for part of a shape is taken from the whole one with `.pick()` or `.omit()` (the track list from `trackSchema`, the artist names from `groupSummarySchema`, the playlist message from `storedPlaylistSchema`, the stream messages from `radioStationSchema`) and one that adds to it with `.extend()`, so a field is described once. A shape that both processes read, like the folder of `shared/schemas/folders.ts`, lives in `shared/schemas/`.
- **Database rows:** schemas in `electron/schemas/rows.ts` and next to the repositories, passed as the third argument of `executeQuery`, which rejects with the fields that are wrong. A JSON column is read by the schema.
- **Queries and settings:** the sorts, folders and search of `shared/types/library-query.ts`, the radio queries and the window of the `tunelle://app` library routes are read by schemas that fall back to a default for a bad value.
- **Messages to the renderer:** `shared/schemas/messages.ts` has a schema for each channel, applied by `onMessage` (`client/services/on-message.ts`), which drops a message that does not match and logs the fields that are wrong. `RESTORE_SETTINGS` is read by `restoredSettingsSchema` (`client/redux/persisted-settings.ts`), which leaves out a key of the wrong type (it keeps its default) and restores the others; `PersistedSettings` is inferred from the same schema, and the reducer only normalizes what a schema cannot (the theme, the equalizer, the cover size).
- **Answers of the routes:** `client/services/library-api.ts` checks every answer with the schemas of `shared/schemas/library.ts` and `loudness.ts`; the whole library is checked too, which costs the same as on the main process (about 130 ms for 50 000 tracks, not measured with `npm run perf`).
- **Loudness:** the analysis (`shared/schemas/loudness.ts`) is checked where it is stored (`jsonOf` in `electron/schemas/rows.ts`), where the measuring page reports it and where the page reads it. The types of the measurement, the radio stations and the update state are inferred from schemas.
- **Files and variables:** `update-preference.json` is read with a schema; the `TUNELLE_` variables are read with `electron/schemas/environment.ts` (a value that does not fit is the default).
- **Playlist message:** the playlist message is read by a schema in `client/domain/playlists.ts`.
- **Services and renderer:** the Deezer answer (`electron/services/artist-photos.ts`) and the items of the favourites and the history (`client/domain/favourites.ts`) are read by schemas. `StoredFavourite`, `StoredHistoryItem` and `StoredPlaylist` are inferred from the schemas in `shared/schemas/`.
- **Library:** the rows of the track lists, the albums, the groups and the format of a track are read by the schemas of `shared/schemas/library.ts`, and `Track`, `AlbumSummary` and `GroupSummary` are inferred from them. A column that holds NULL reads as empty text. Parsing 50 000 track rows takes about 130 ms, next to a query on that many rows.
- **Radio and MusicBrainz:** the answers of the station directory and of the recording search are read by schemas in `electron/services/radio-browser.ts` and `radio-art.ts`.
- **Routes:** the parameters of `/track` and the names of the assets are read by `electron/schemas/routes.ts`.
- **Not covered:** the settings the main process saves, which stay an object that it stores as it is (a key from a newer version has to survive a downgrade).
