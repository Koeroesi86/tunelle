# Integration tests

`electron/**/*.integration.test.ts`, `scripts/**/*.integration.test.ts` and `.claude/hooks/*.integration.test.ts` are the Vitest project `integration` (`npm run test:integration`). It sits between the unit tests and `e2e/`: the code of the main process runs against the real things around it, in Node and without Electron.

- **Real:** SQLite (`createTestDatabase()`, all migrations applied), the files of `e2e/fixtures/`, `music-metadata`, and the ffmpeg of this system (`.cache/ffmpeg/install/bin`, `npm run ffmpeg` builds it, CI downloads it).
- **Replaced:** only the `electron` module, with `vi.mock('electron')`: where the app is (`app.getAppPath()`), where it writes (`app.getPath()`), and a utility process that answers with the code of the worker in the same process.
- **Not in the unit tests:** they mock the metadata, the database or the decoder, so a change that breaks only the cooperation of two parts passes them.

`decoded-track.integration.test.ts` scans a fixture folder of each format that Chromium does not play, then decodes the tracks the library holds and checks the pitch, the length and the sample width of the WAV.

`decoded-loudness.integration.test.ts` measures the decoded WAV of each format with `measureBlocks` and `summarise` of `client/loudness/`, the code the hidden window runs, and compares the level with an ideal sine of the pitch and amplitude the fixture was made with (0.125, DSD 0.5). The ideal sine of half the full scale is checked against -9.7 LUFS, the figure that `e2e/functional/loudness.spec.ts` expects from Chromium, so the two environments are tied by one number. Chromium's resampler in `decodeAudioData` is replaced by a cubic one in `electron/test-wav.ts`; what only Chromium can show (24 bit at 88.2 kHz) stays in `e2e/functional/dsd.spec.ts`.

`persistence.integration.test.ts` (in `electron/listeners/`) registers the listeners of the favourites, the history, the playlists and the settings on a database file, closes it, opens it again and asks as the window does (`FAVOURITES_LOAD`, `APP_READY`), so what the listener keeps is tried across a start of the app. That the window sends the right message is tried by the tests of the client (`middleware.test.ts`, `PlayerHome.test.tsx`), and `e2e/collections.spec.ts` keeps the restart of one playlist for the whole app.

The test once failed on windows-2025 with `expected 1 to be greater than 1` in `ask` ([#377](https://github.com/Koeroesi86/tunelle/issues/377)): the `vi.waitFor` gave up after its default 1 s. The listeners answer only after the database write and the availability check (`register-favourite-listeners.ts`), so the reply was late on a slow runner and not sent before the write; `ask` waits with an explicit `timeout` of 15 s. If the reply is missing after that, look for a `logError` of the listener, as `reply` catches the error of the work.

`scan-folder.playlists.integration.test.ts` (in `electron/library/scan/`) scans a folder of the mp3 fixtures with a playlist file in it, and checks what no unit test can: the playlist is made after the tracks are stored (so its entries are the tracks of the library, not only the file names), a file that did not change is not read again and the window is told only when a playlist changed, a deleted file takes its playlist with it in a deep scan and not in a shallow one, and a folder that is not scanned leaves the playlists of other folders alone. `write-playlist-file.integration.test.ts` writes real files: the `.bak` of the first write, no temporary file left after a failed write, and a read only folder (skipped on Windows, which takes no mode of a folder, and for the super user, who is held back by none). `playlist-sync-migration.integration.test.ts` runs migration 019 over a database that has playlists with and without a file. What these do not cover: a folder that goes offline (the scan does not list it, see [playlist-import.md](../app/playlist-import.md)), the save and open dialogs (native, so `register-playlist-listeners.test.ts` checks what they are given and what is done with their answer), and a scan that runs while a write back writes the same file.

`library-sync.integration.test.ts` (in `electron/library/scan/`) adds a folder of FLAC files to the library with the real scan, queue, SQLite and files, then changes the disk and asks as the app does: a rescan picks up an added file, rescans a file whose size or modification time changed and skips one whose size and time are the same, `rescanChanges` takes the places that the watch reports (added and removed files), `removeFolderFromLibrary` leaves the files, and `checkFolders` marks a folder that was moved away as offline, keeps its tracks and finds them again when it is back. The utility processes of the reader of the tags and of the look at a folder (`mount-probe-worker`) run in the test process, and the queue is started as the app starts it (`backgroundQueue.start()`; without it every scan waits for ever and the hook times out). `addFoldersToLibrary` drops a path without `lastModified`, so the test passes one. Six end to end tests that started the app for each of these cases are gone; `e2e/functional/library.spec.ts` keeps the one with the real watch of the system, as `fs.watch` differs by system.

`subsonic-client.integration.test.ts` (in `electron/services/sources/`) runs the client and the `/source/audio` route against a small Subsonic server on `127.0.0.1` that checks the token as Navidrome does, and against an https one with a self-signed certificate. A unit test mocks the sockets, so it can not show that a range is really cut and answered with a 206, that a server which has stopped fails and does not hang, or that only the certificate the user approved is accepted. It is not a test against a real Navidrome, which has not been tried (see [sources.md](../app/sources.md)).

What was looked at and kept in `e2e/`: the range and the path checks of `tunelle://app/track` (`system.spec.ts`) because `net.fetch` of a file differs in Electron and Node, and the loudness tests (`loudness.spec.ts`, `dsd.spec.ts`) because the measurement runs in a hidden window of Chromium. Of the remote listening, `remote.spec.ts` keeps three tests of two apps (listen along with pause and play, revoke, skip with the granted control), as the audio element of a listener is what ended up playing after a revoke; the follow of a next track and of a seek is in `use-remote-follow.test.tsx` and `listener-client.integration.test.ts` ([remote-listening-test-plan.md](remote-listening-test-plan.md)). The tests of the background tasks pill, and of the liked and recently played pages, are gone from `e2e/`: `QueueIndicator.test.tsx`, `register-background-task-listeners.test.ts`, `FavouritesView.test.tsx`, `HomeView.test.tsx`, the reducers and `persistence.integration.test.ts` cover each layer.

## What is an integration test, and what is not (#388)

Only what a unit test can not show is one ([unit-tests.md](unit-tests.md) says it first: unit test everything with mocks, integration only for what they can not cover, end to end only where neither can). The 66 unit tests that used the real system were each mocked or moved here, and most of the moved ones kept a unit test of the logic next to them (`name.test.ts` and `name.integration.test.ts` for the same module). What stayed here, and why a mock does not show it:

- **`electron/database/`, `electron/repositories/`:** the SQL against SQLite and all the migrations (`createTestDatabase()`); a mocked `execute-query` returns what the test says, whatever the query is. The unit tests of the repositories check which queries and parameters go out.
- **`electron/library/scan/`, `electron/library/watch/`, `mounts/`, `art/`, `loudness/`:** the scan, the queue, the files and the database working together (a rescan of a changed file, a folder that goes offline, the order of the stored rows); `fs.watch` differs by system. The unit tests of `scan-folder`, `rescan-library`, `rescan-changes` and `folder-watcher` check the decisions with the memory file system and the mocked repositories.
- **`electron/protocols/`, `electron/listeners/`, `electron/remote/`, `electron/services/`:** a route over a database that has rows, a listener that keeps its data across a restart, the radio over a real stream, the AppImage launcher entry started by the shell, and the swap script of the macOS update (`mac-update-source.integration.test.ts` runs the real `sh`).
- **`scripts/`:** a script that starts a real process (the command line of `version.js`), builds a real tree (`build-site`, `generate-icons`, `alias-paths`) or reads the whole repository (`unit-test-isolation`).

A test that only needed a folder to write into, a clock, a child process or a port is not here: it is a unit test with `memoryFs`, fake timers, `child_process` mocked and a server that never listens.

The `integration` project loads `electron/test-utility-process.ts` as its setup file, as the `backend` project does: the scan tests start the tag reader in a utility process, and without the fake one the first scan fails with `Cannot read properties of undefined (reading 'fork')` and the run goes on until it is out of memory. Check it with `npx vitest run --project integration electron/library/scan`.

Coverage: `npm run test:coverage` does not run this project, so a line that only an integration test reaches counts as not covered. Counting it was tried (the first version of #388 moved all 66 files here and added `--project integration`) and dropped: the number then says nothing about the unit tests, and a mocked unit test is the one that fails in a few milliseconds.

`sliced-loudness.integration.test.ts` (in `electron/protocols/`) measures a 13 minute WAV in pieces with `measureSliced`, on a real file that a stub of `fetch` serves in ranges, and checks that the level is the one of the whole file. It replaced the end to end test of a 50 minute file, which waited for a hidden window to decode it. The stub is set in the test, not in `beforeAll`: the project restores the globals before each test (**symptom:** every read was `unreadable` and the stub was never called). The software rendering tests and the restart of the library are gone from `e2e/` too: `gpu-acceleration.test.ts`, the reducer and the theme provider cover the first, `collections.spec.ts` restarts the whole app and `library-sync.integration.test.ts` covers the stored library.

## What stays in `e2e/`

One played format per decoder path (`alac.spec.ts`, and `dsd.spec.ts` for 24 bit at 88.2 kHz); every other format is a row of `formats` in `decoded-track.integration.test.ts` (tags, codec, sample width, length, pitch) and of `decoded-loudness.integration.test.ts`, and has no end to end test of its own (FLAC, Opus, Vorbis, MP2, AC-3 and WAV had one each, which played the same path as ALAC through the same decoder proxy). A new format is a fixture folder and one row in each, not a spec. `gapless.spec.ts` keeps FLAC (the decoder path) and AAC (played by Chromium); MP3 is decoded like FLAC, and its length is checked in the integration test. Whatever else needs Chromium or the operating system around the app: sound leaving the app, the loudness measurement (it runs in a hidden window, see [loudness-measurement.md](../app/loudness-measurement.md)), the window, the `tunelle://` scheme as Electron registers it, and the preload. A test here cannot see a difference between Node and Electron (`net.fetch`, streams, `app.isPackaged`), so a behaviour that depends on one is an end to end test.

## In CI

A step of the `test` job of `test.yml` after `npm run test:coverage` and before the build, on every system. `required-checks` of `pr-checks.yml` needs `test`, so the step is a required check without a rule of its own. `npm run test:coverage` runs the projects `backend` and `frontend` only; `npm test` runs all of them (the unit tests are in [unit-tests.md](unit-tests.md)).

A new test file is named `name.integration.test.ts` and goes next to the code it tests. Read the sine fixtures in [e2e/fixtures/README.md](../../e2e/fixtures/README.md) before adding a format.
