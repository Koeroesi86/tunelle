# Containers

`client/containers/` holds the components that are connected to the Redux store (`connect`, `mapState`, `mapDispatch`) and to the audio context. `client/components/` holds the views they render, which take props and callbacks only, so a view is tested and reused without a store.

- A container mirrors the folder of its view: `components/pages/home/HomeView.tsx` is wrapped by `containers/pages/home/index.tsx`, and the other files that import the page import the container.
- The test of a container (`index.test.tsx`, with a store from `createStore`) lives beside it; the test of the view stays in `components/`.
- Every connected component is in `containers/`. `components/` does not import `react-redux`, `redux/`, `services/` or `backend/` (lint, `no-restricted-imports`, one block for all of them): what a view needs of the store besides props (the page cache, the navigation types, `browseKey`, `pageRequest`) is in `domain/`. What a component imports is checked the same way, so no path leads to the store or the backend: `hooks/`, `domain/` and `utils/` do not import `containers/`, `react-redux`, `redux/`, `services/` or `backend/` either; the tests of `components/`, `hooks/`, `domain/` and `utils/` follow it too, so a view or a hook is tested with props and stubs and a connected one in `containers/`; the fetching of what `domain/` describes is in `services/` (`favourite-tracks`, `source-tracks`, `group-tracks`) and the selectors of the store in `redux/library-query.ts`.
- A new connected component is a view in `components/` and a container beside the same path in `containers/`.
- A view of the local library can be given another source: the parts that are specific to the local library are props (`openAlbum`, `playAlbum`, `fetchAll`, optional `selected` and `folders`) which the local containers fill (`containers/library/local-album.ts`). The containers `source-albums`, `source-artists` and `source-tracks` give the same views the page caches of a server in `state.sources.lists`, from a `SourceBrowse` request (see [sources.md](../app/sources.md)).
- What belongs to where the items are from is a slot, a render prop that a container fills and that stays a module function (a row is memoized): `renderActions` of `AlbumView` (the buttons on the corners of a cover), of `TrackView` (the favourite, playlist and queue buttons of a row) and of `AlbumDetails`, `renderCoverMenu` of `AlbumDetails`, and `renderAlbums` and `renderOpenParts` of `GroupView` (the albums of an open group and the photo, its menu and the sort in its bar). The local ones are in `containers/library/item-actions.tsx` and `local-group.tsx`; a list that omits a slot shows nothing there. The pages take the same kind of slot: `renderFavourite` (the heart, `containers/ui/render-favourite.tsx`) and `addToQueue` for the favourites, the playlist, the radio, the home and the now playing pages, `renderLoudness` for the now playing page, `panels` and `controls` for `LocalCollection`, and `renderAlbums`, `renderArtists` and `renderTracks` for `SourceLibrary`, and `radio`, `nearby`, `renderServers` and `renderLibrary` for `OnlineSources`. `TitleBar` takes `actions` (the queue and the window controls). The layout takes slots as well: `PlayerHome` takes `renderTitleBar`, `renderNavigation`, `renderTabs`, `controls` and `overlays`, and `PlayerTabs` takes `pages`, `renderLocal`, `settings` and `overlay`; `containers/layout/player-home` and `player-tabs` are where the app is composed. A server album has no buttons on its cover, and a server track only the queue buttons: the favourites and the playlists keep tracks of the library, and the availability check reports a server track missing (`electron/library/watch/favourite-availability.ts`). `LoudnessPanel` takes `fetchAnalysis`, `ArtistPhoto` takes `fetchCover` and `RemoteListener` takes `resolveUrl`, the containers pass the service functions. `GroupView` takes `fetchTracks` (the tracks of an open group). The hooks that reach the backend, the media controls of the system, MPRIS and the hosts that listen, (`use-media-session`, `use-mpris` and `use-remote-host`) are in `containers/layout/player-integrations`, a component that shows nothing, so `PlayerControls` and the other components do not read the backend. The address of a cover is a route (`coverRouteOf`, `radioLogoRouteOf`, `toNowPlaying().cover`): a component resolves it with `useResolveUrl()` from `hooks/use-resolve-url`, whose context the app root fills with `localUrl` and which gives the route back without a provider, and the containers and the store resolve with `localUrl` themselves. No component of `client/components/` imports a container (lint, `no-restricted-imports` with a pattern).

## Testing a container

A container is tested for what it gives its view and what the view's callbacks do, not for what the view draws.

- `renderContainer` of `client/test/render-container.tsx` renders it over a store of the app, in the state the test makes of the first one, and `sent()` gives the dispatched actions. The store has no middleware, so nothing reaches the backend.
- The view is mocked as `vi.fn(() => null)`, and `propsOf(View)` reads what it got the last time. A test file of its own in the folder of the container does this; a test in the folder above may render the view with a stub instead.
- A container that renders other containers has them mocked as named functions, and the test compares the elements (`toEqual(<TitleBar {...slot} />)`), which also tells two stubs apart.
- `audio/context.ts` makes an `AudioContext` as it is loaded, which jsdom does not have: mock the module, with `Audio: createContext(…)` of values the test looks for.
- A dispatch outside `act` does not render again at once, so check the action, not the next props.

What the connection middleware does with each action and each message of the main process is a table in `client/redux/connection/middleware-messages.test.ts`. A new incoming channel needs a row, or the typecheck fails.

## A merge function drops the own props

A third argument of `connect` replaces the default merge, so the props the parent passes reach the view only if the function returns them.

- Symptom: a compact window had no menu button, so its navigation could not be opened (#618).
- Cause: the merge function of `containers/layout/title-bar` left out `onMenu` and `menuOpen`. The tests of `PlayerHome` replace the title bar, and those of `TitleBar` pass the props to the view.
- Check: the test of a container with a merge function passes every own prop and looks for it at the view.
