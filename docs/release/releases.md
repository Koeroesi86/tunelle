# Releases

Releases come from `release.yml`: Monday and Thursday 06:00 UTC and by hand, from `master` only. A scheduled run skips when only docs or `.github/` changed since the latest `vYY.M.N` tag. The published release is what installed apps update from, see [updater.md](../app/updater.md). After every release it publishes it calls `store.yml`, see [microsoft-store.md](microsoft-store.md). Each release carries a short summary of its changes, see [release-notes.md](release-notes.md). A job of a release that no runner takes is run again by `watch-unstarted-jobs.yml` (and `retry-unstarted-jobs.yml` on a schedule), see [ci.md](../development/ci.md#jobs-that-no-runner-takes).

## The version (`scripts/release/version.js`)

The version is `YY.M.<run number>` (for example 26.10.14), stamped into `package.json` in the packaging job. Never edit `version` by hand.

- `node scripts/release/version.js` prints the version of a new release, from `GITHUB_RUN_NUMBER` and today.
- `node scripts/release/version.js --after <latest>` does the same, but fails when it is not greater than the latest release (empty: no release yet).
- `node scripts/release/version.js <version>` writes that version to `package.json`, so the package, `latest*.yml` and the release agree.

It is valid semver for electron-updater: no zero padded month and no prerelease part, which it would take for an update channel; and small enough for the numbers of a Windows file version. The plan job refuses a version that is not greater than the latest tag.

`release.yml` must not be renamed or recreated: its run number would restart, and the version with it.

## Pull requests and `master`

`master` requires up to date branches. Pull requests with auto-merge on are rebased onto `master` one at a time: only the one whose auto-merge was enabled first is looked at, and it is rebased when it is behind (`rebase-auto-merge.yml`, `scripts/release/rebase-auto-merge.js`). The ones after it wait until it merges or its auto-merge is turned off, also when its checks fail or it has a conflict, so that the author fixes it first. One conflict is solved by the script: when the pull request was stacked on one that was squash merged, its branch still holds the commits of that one, which are not in `master` as they are (the squash is one new commit), so GitHub's rebase replays them and conflicts. The script finds the commits at the start of the branch that belong to a merged pull request, takes the last of them as the old base, and runs `git rebase --onto origin/master <old base>` in the checkout of the workflow (`fetch-depth: 0`), then pushes with `--force-with-lease` on the head it saw. A commit belongs to a merged pull request when `/commits/{sha}/pulls` lists one, or when its author date and message are those of a commit of one of the last 30 pull requests merged into `master`: a pull request that was rebased before its squash merge (by this script or by hand) has new shas, so the old copies in the branch above it are no longer listed under it, which left the old base too early and the replay conflicting on the commits of the pull request below (#454 on #453, run 44309676794). A rebase keeps the author date and the message, which is why they match. A conflict of the own commits of the pull request, a branch from a fork, or no merged pull request below still waits for the author (the rebase is aborted, nothing is pushed). Only the first 100 commits of the branch are looked at, and the replayed commits are unsigned, as the rebase of GitHub signs and this one does not. The state of the checks is not looked at. It pushes with the `GH_REBASE_TOKEN` secret, as a push with `GITHUB_TOKEN` starts no checks.

A pull request of a stack cannot get auto-merge while its base is another pull request. The `automerge` label asks for squash auto-merge instead: `automerge-label.yml` (`scripts/release/automerge-label.js`) turns it on for the open pull requests to `master` that have the label, are not drafts and are not from a fork. It runs when a pull request is opened, reopened, marked ready, labeled or has its base edited, when `master` moves and when the checks of a pull request end, so it also catches a pull request whose base became `master` after the one below it merged (the docs of GitHub do not say which event that retarget sends, and a push to `master` can come before it, hence the last two). It does this once: it takes the label off after it turned auto-merge on, so auto-merge that is turned off by hand stays off, and removing the label does nothing. The rebase of `rebase-auto-merge.yml` then takes over, and both use `GH_REBASE_TOKEN`, as auto-merge turned on with `GITHUB_TOKEN` starts no workflow. There is no schedule, a run missed by an event is started by hand (`workflow_dispatch`).

## Signature of the macOS update file

`release.yml` signs the merged `latest-mac.yml` with the secret `UPDATE_SIGNING_KEY` of the environment `release` and uploads `latest-mac.yml.sig` with it; the macOS app installs nothing without a valid signature, see [updater.md](../app/updater.md). Without the secret the release goes out unsigned and macOS apps stay on their version.
