# Supported formats

The library scan keeps the files whose extension is in `supportedFormats` of `electron/utils/is-supported.ts`: `flac`, `mp3`, `wav`, `aac`, `ogg` (also `oga`), `opus`, the MP4 family (`m4a`, `m4b`, `m4r`), `ape`, `wv`, `aif`, `aiff`, `aifc`, `dsf`, `dff`, `wma` and `asf`.

These are the formats that Chromium plays in an `<audio>` element and decodes with `decodeAudioData`. The list is what the player can play, so a file the player cannot open is not in the library.

Formats that were in the list and are not played, checked in Electron 44 with generated files and with files of a real library:

- `wmv`, `mp2`, `m2a` and `wvp` (`ape`, `wv`, `aif`, `aiff`, `aifc`, `dsf`, `dff`, `wma` and `asf` are decoded by the proxy, below): `<audio>` fails with `MEDIA_ERR_SRC_NOT_SUPPORTED`, `decodeAudioData` with `EncodingError`.
- `m4p` (protected by FairPlay, which Chromium cannot decrypt), `3gp` (AMR audio, which Chromium does not play on desktop), `ogx` (Ogg that may hold Speex or Theora) and the video containers `mp4`, `m4v` and `ogv`, which hold films and clips, not music (this is an audio player). They are out of the list until the decoder proxy of issue 302 plays them.
- Opus (`.opus`, and Opus in an `.ogg` or `.oga`, codec `OPUS`) is decoded by the bundled ffmpeg (the native `opus` decoder, no libopus) ([#469](https://github.com/Koeroesi86/tunelle/issues/469)). It is not an expired codec but a royalty-free one: Xiph, Broadcom and Microsoft grant royalty-free licences for conforming implementations, and Vectis IP's pool (2023) says open implementations and apps are not affected (see the Patents section of [ffmpeg-build.md](../development/ffmpeg-build.md)). Opus always decodes at 48 kHz, so the WAV is 48 kHz whatever the rate of the source; the pre-skip is trimmed by the Ogg demuxer, so the decoded WAV of the fixture is its 6 s (`decoded-track.integration.test.ts`). Not progressive, like Vorbis. Opus in a WebM or Matroska file is not part of this ([#350](https://github.com/Koeroesi86/tunelle/issues/350)).
- MP3 (`.mp3`, codec `MP3`) is decoded by the bundled ffmpeg (the native `mp3float` decoder, no LAME), so it sounds the same on every system ([#470](https://github.com/Koeroesi86/tunelle/issues/470)). The patents of Layer III are reported expired (the licensing programme of Technicolor and Fraunhofer ended on 23 April 2017, see the Patents section of [ffmpeg-build.md](../development/ffmpeg-build.md)). The `mp3` demuxer reads the ID3 tags and the Xing or LAME header and trims the encoder delay and the padding, which `e2e/functional/gapless.spec.ts` checks with the `e2e/fixtures/mp3/` fixture (the decoded WAV of it is the 6 s of the source in `decoded-track.integration.test.ts`). MP2 (`MPEG 1 Layer 2`) is a different codec ([#347](https://github.com/Koeroesi86/tunelle/issues/347)) and stays with Chromium. The length in frames is not exact before the decode (the time base of the stream is not one frame), so MP3 is not progressive: the first play waits for the whole decode, and the WAV is about 11 times the file at 128 kbit/s. The decode of the fixture is the same, sample for sample, as the one of a full ffmpeg.
- WAV (`.wav`) is decoded by the bundled ffmpeg too ([#467](https://github.com/Koeroesi86/tunelle/issues/467)), so every file takes the same path whatever Chromium does with it. Measured on 2026-11-24 in the Electron of the app (`decodeAudioData` and an `<audio>` element, 1 s sine made with ffmpeg): Chromium plays 8, 16, 24 and 32 bit integer PCM, 32 bit float, `WAVE_FORMAT_EXTENSIBLE` (6 channels), µ-law and A-law, and fails on 64 bit float, Microsoft ADPCM and IMA ADPCM. The scan names them by what `music-metadata` reads: `WAV` (integer PCM, also extensible), `IEEE_FLOAT` (32 and 64 bit), `ADPCM` (Microsoft), `DVI_ADPCM` (IMA), `ALAW` and `MULAW`, and all six are in `decodedCodecs`. The decoded WAV keeps the depth of the file up to 32 bit (8 bit and ADPCM give 16 bit, 32 and 64 bit float give 32 bit integer). PCM and float WAV are served while they are decoded (progressive); the ADPCM, A-law and µ-law ones wait for the decode. `RF64` and files over 4 GiB decode with the same demuxer, but `music-metadata` cannot read the tags of an RF64 file, so the scan does not keep it (not changed here). The decoded copy of a PCM WAV is as big as the file and counts against the 2 GiB cache like the others. A WAV that holds MP3 or another compressed codec (`MPEGLAYER3`, GSM) is not in the list and is still played by Chromium.
- Ogg Vorbis (`.ogg`, `.oga`, codec `VORBIS`) is decoded by the bundled ffmpeg (the native `vorbis` decoder, no libvorbis) like FLAC, so it sounds the same on every system ([#468](https://github.com/Koeroesi86/tunelle/issues/468)). Vorbis is royalty-free (Xiph), so there is no patent question. Ogg trims the start and the end by the granule positions, so the decoded WAV of the fixture is the 6 s of the source (`decoded-track.integration.test.ts`) and gapless playback needs nothing more. The length in frames is not exact before the decode, so Vorbis is not progressive: the first play waits for the whole decode and the WAV is about 8 to 10 times the file.
- FLAC (`.flac`, and Ogg FLAC in an `.ogg` or `.oga`, codec `FLAC`) is decoded by the bundled ffmpeg, not by Chromium, so it sounds the same on every system and the decode is ours. It goes through the decoder proxy ([decoder-proxy.md](decoder-proxy.md)) like the formats below, keeps the bit depth of the file (16, 24 or 32 bit PCM) and leaves the cover art out of the WAV. FLAC has no encoder delay or padding, so there is nothing to trim for gapless playback.
- ALAC in an `.m4a` is not decoded by Chromium, and plays through the decoder proxy ([decoder-proxy.md](decoder-proxy.md)), which decodes it with ffmpeg to a WAV file first.
- Monkey's Audio (`.ape`, told apart by the codec `MONKEY'S`, the first word that `read-audio-format.ts` keeps) plays the same way, decoded with ffmpeg to WAV first. The high compression levels decode slowest, so the first play of a long file waits for the whole decode ([decoder-proxy.md](decoder-proxy.md)).
- WavPack (`.wv`, told apart by the container name `WavPack`, which `read-audio-format.ts` shows for the `PCM` codec of `music-metadata`) plays the same way, including the hybrid lossy mode. A WavPack file that holds DSD is kept out (codec `DSD-WAVPACK`), as DST, the compressed DSDIFF, is (codec `DST`).
- AIFF and AIFC (`.aiff`, `.aif`, `.aifc`) play the same way. The scan names them by the container, `AIFF` or `AIFF-C` (AIFC with byte swapped PCM, which iTunes writes as `sowt`, whose `lossless` flag `music-metadata` reads as false). The build has the big and little endian integer and the float PCM decoders for them ([ffmpeg-build.md](../development/ffmpeg-build.md)).
- DSD (`.dsf`, and `.dff` of DSDIFF) is stored as codec `DSD` with 1 bit and the rate of the file, and plays the same way, decoded to 88.2 kHz and 24 bit ([decoder-proxy.md](decoder-proxy.md)). DSD is converted to PCM, not played natively.
- WMA (`.wma`, and audio in an `.asf`) is stored as codec `WMA` and plays the same way, decoded with ffmpeg to WAV first. It covers WMA 1, 2, Pro and Lossless; WMA Voice and Speech (codec `WMA-VOICE`) are kept out. The patent that describes the codec, [US 7,158,539 B2](https://patents.google.com/patent/US7158539B2/en), has expired; see the Patents section of [ffmpeg-build.md](../development/ffmpeg-build.md). `.wmv` is video and stays out.
- AC-3, Speex and Theora (video) in a container that has a supported extension (`.m4a`, `.ogg`) are not decoded. They are told apart by the `codec` read from the file (`isSupportedCodec`), so the scan does not store them, and a rescan removes one that an earlier version stored. A folder with such files is read again by each scan of that folder, as nothing is stored to tell that the file is unchanged.

A track of a format or codec that left the list is removed from the library by the next rescan (`removeMissingTracks` in `electron/library/scan/rescan-library.ts`), together with the tracks whose file is gone. The file itself is not touched.

Before a format is added, test it with `<audio>` and `decodeAudioData` in the app, not with `canPlayType`, which answers an empty string for formats that play.
