# Remote access: the code of the host

The pieces of `electron/remote/` and the screens of the host. Part of [Remote access: discovery, certificate and now-playing route](remote-access-discovery.md).

## The code so far

`electron/remote/` holds the pieces the proof settled, with tests (second and third to fifth pull request of #360, nothing calls them yet):

- `dns-packet.ts`: the mDNS wire format. `decodeMessage` returns `undefined` for a cut or made up packet (bounds, a limit on name pointers) instead of throwing, as the socket handler must not throw into the main process.
- `certificate.ts`: `createHostIdentity`, `approvalCode` and the pinning options. `certificate.integration.test.ts` runs them against a real TLS server: the pinned certificate is answered, another one is refused, and the first contact reads the same code as the host shows.
- `access.ts`: who may listen. `AccessControl` keeps the waiting requests, the approved devices and the blocked ones in memory, and `snapshot()` is what the host writes to disk (the hash of the secret, never the secret; `host-store.ts` writes it). A request is checked in this order: rate limit per address (5 a minute, counted before the body is read, so garbage counts too), the schema (device id, name up to 60 and note up to 200 characters, control characters turned into spaces), blocked, already approved, the pending limit (5, a device that already waits does not need a new place) and only then a prompt. Waiting requests expire after ten minutes. The note is kept as it was sent, apart from the control characters: showing it as text is the job of the screen. A device id is made by the listener, so a blocked device that picks a new id is a new device; blocking by address is not done, as addresses on a LAN change and are shared behind one router.
- `host-routes.ts` (the two routes and the now playing, unit tested without a socket), `now-playing.ts` (its schema) and `host-server.ts`: the HTTPS server of the host (`startHostServer`), built on the certificate and `AccessControl`. Five routes exist and every other path and method is a 404: `POST /remote/request` (the listener's request; 202 waits, 200 approved, 400 invalid, 403 blocked, 429 rate limited, 503 full) and `GET /remote/now-playing` (the device id in `x-tunelle-device` and the secret as `Authorization: Bearer`, else 401, or 429 for an address with too many wrong secrets) and `GET /remote/events` (the same credentials; a server sent events stream that sends the now playing at once and again at each change, with a `: ping` every 25 s). A stream is checked against the access control at each event and ping, and the host controller calls `closeRevoked()` after every decision on a device (approve, deny, revoke, block) and every change of controls, so a device that was revoked or blocked loses its event stream and the audio on its way at once, not at the next event; at most 20 streams are open (503 after that). The polling route stays for a listener that cannot keep a stream. `POST /remote/control` takes one command (`control-command.ts`: `playPause` with `play`, `pause` or `toggle`, `skip` with `next` or `previous`, `seek` with a position in seconds, `volume` with a level from 0 to 1) with the same credentials: 401 for a device that is not approved, 400 for a command that is not valid, 403 when the host did not allow that control for that device (the approval alone gives none), else 200 and the command goes to the page as `REMOTE_CONTROL`. `queue` is a control that the host can grant, but no command exists for it yet: a listener cannot reach the library of the host, so what it would add is still open. The page that acts on `REMOTE_CONTROL` comes with the renderer part. `GET /remote/audio` (same credentials) serves the file of the track that plays now, with the range of the request (206 and `Content-Range`, so a listener can seek): the page sends the library path of the track beside the snapshot in `REMOTE_STATE` (`path`), the host keeps it and never puts it in the now playing, and no request names a file, so a listener reaches that one track and nothing else of the library. It is 404 while nothing plays or no path came. It is the same lookup as `tunelle://app/track` (`serveTrack`: the path must be in the database, and a format that Chromium does not play is decoded first), and `relay-response.ts` writes the fetch answer to the node response; a body that fails destroys that response only, and a listener that goes away aborts the decode. A body is read up to 4 KB. A handler that fails answers 500, and a socket or TLS error ends that socket, so nothing reaches the main process as an unhandled error. `loopbackOnly` binds `127.0.0.1`.
- The secret reaches the listener on its next request after the approval: the approved answer carries `secret` once, and later answers do not. The listener polls its request until then. Whoever knows the (random, 128 bit) device id could pick the secret up first, and only the host and the listener know it; a revoke or block before the pickup drops it. Wrong secrets are limited per address: `authorize(address, deviceId, secret)` counts the wrong ones (10 a minute), and past the limit even the right secret gets 429 until the minute is over, so a guess is not free (the secret is 256 bits, so guessing was no route anyway, but the limit stops a flood of hashing). The right secrets of a listener that asks every second are not counted.
- `host-server.integration.test.ts` runs the flow against the real server with a pinned client: waiting, denied, unknown, approved, revoked and blocked devices, a hostile and an oversized note, a flood (rate and pending limits), library paths and `../`, and a closed server that refuses the connection.
- `listener-client.ts`: the other end, in the main process of the listener. `contact` is the first contact (a request without credentials over an unpinned connection, which gives the certificate and the code for both screens), `requestToListen` and `fetchNowPlaying` run pinned (a changed certificate fails with `self-signed certificate`), and `followNowPlaying` resolves `revoked` for a 401, which is what a revoked, blocked or not yet approved device sees. Answers are cut at 64 KB, a call times out after 5 s, and the answer is read through Zod. `expectedPosition` runs a playing snapshot on from its time (never backwards), and `driftCorrection` gives a position to seek to only when the listener is more than 0.5 s away, so the audio clock does the small steps. `listener-client.integration.test.ts` runs it against the real host server.

- `host-store.ts`, `host-controller.ts` and `host-requests.ts` (part 6): what the host keeps and how the app drives it. Files sit in `<app data>/remote/`: `host.json` (settings: `enabled` off by default, `name`, `loopbackOnly`, and the `port` of the last start), `devices.json` (the `snapshot()` of `AccessControl`, so the hash of the secret and never the secret), `host-certificate.pem` and `host-key.pem` (mode 0600; made on the first start, and deleting them makes a new certificate that listeners refuse until approved again). A stored file that is cut or has a wrong part falls back to the default of that part. `createHostController` starts and stops the server by the settings (nothing listens while `enabled` is false), reuses the saved port and takes a free one when it is taken, writes the devices after every approval, revoke, block or change of controls, and reports a `HostState` (settings, whether it runs, the code, the waiting requests without their address, the devices and the error of a failed start) through a callback. A request that starts to wait reaches the callback at once (`ObservedAccess`).
- `register-remote-listeners.ts`: the channels between the page and the host. The page sends `GET_REMOTE_HOST`, `SET_REMOTE_HOST` (parts of the settings), `DECIDE_REMOTE_DEVICE` (`approve`, `deny`, `revoke`, `block` for a device id), `SET_REMOTE_DEVICE_CONTROLS` and `REMOTE_STATE` (the now playing); the main process answers with `REMOTE_HOST_STATE`. A message of the wrong shape is dropped. The player sends `REMOTE_STATE` and acts on `REMOTE_CONTROL` (see below); the settings screen and the question about a device that waits are described next.
- `client/hooks/use-remote-host.ts` (part 8, in `PlayerControls` beside `useMpris`): sends `REMOTE_STATE` when the track, its path or whether it plays changes and on a seek (the position is more than 1.5 s from where the playback would be), `idle` when nothing plays, and no `duration` and no `path` for a station (it has no file to relay). It listens once for `REMOTE_CONTROL`, reads the command through the same schema as the main process, drops one of the wrong shape and calls what the player has now (`playPause` with `toggle` follows `isPlaying`). The hook works without a backend (the detached one sends nothing), as `useMpris` does. Check: `npx vitest run --project frontend client/hooks/use-remote-host.test.tsx`.
- The settings (part 8b): `REMOTE_HOST_STATE` is read through `shared/schemas/remote-host.ts` (a message of the wrong shape is dropped, as for every channel) into `uiState.remoteHost`, which is `undefined` until the main process answers `GET_REMOTE_HOST` (sent when the page starts). `settings/remote-access/RemoteAccess.tsx` is the tile: the switch, the code (only while the host listens, so a stale one is not shown), the error of a failed start, the devices that wait (approve, deny; the note is shown as text) and the approved ones (revoke, block, and a checkbox for each of `playPause`, `skip`, `seek` and `volume`; `queue` is not offered while no command exists, and a toggle keeps the controls it does not list). A blocked device shows `Unblock`, which is a revoke: the next request of it needs a new approval. `layout/remote-request/RemoteRequest.tsx` asks about the first waiting device on whatever page is open (the same `Confirm` as the launcher offer), with the code and the note; the next one is asked after the answer. `CONTROLS` moved to `shared/constants/remote-controls.ts` so both sides use one list, and `host-controller.test.ts` checks that `HostState` passes the schema. The tile also has the name shown to other devices (a text field, sent when it is left or on Enter, as a change restarts the host and a name that is empty or the same is not sent; the schema of `host-requests.ts` allows 1 to 60 characters after trimming) and a checkbox for `loopbackOnly` (the host binds `127.0.0.1` and is not announced, so the label says that other devices will not find it). The website section waits for the part that lets a second instance listen, as the feature is not usable from the app before that.
- Host settings (part 12): `host.json` also keeps `maxListeners` (1 to 50, default 5, `shared/constants/remote-limits.ts`). The server counts devices that have an event stream open and answers 503 `full` to a new one past the limit; a device that connects again before its old stream is gone keeps its place. A listener that only polls `/remote/now-playing` is not counted until it moves to the stream. The tile has the limit and the port as numbers (sent when the field is left, out of range or equal values are not sent; a change restarts the host, and a port that is taken is replaced by a free one, as before), a `Disconnect` button that ends what a device has open and leaves it approved (it may connect again; nothing is written), the hint that the system may ask for network access (shown while the host listens beyond this computer) and the help text for when no device can connect (firewall, the macOS local network permission, client isolation, or typing the address), shown while no device was approved. Detecting a blocked network by itself is not done.
