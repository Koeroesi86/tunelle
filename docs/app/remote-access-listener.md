# Remote access: the code of the listener

Pairing, the audio of the host, following it and discovery. Part of [Remote access: discovery, certificate and now-playing route](remote-access-discovery.md).

- `listener-store.ts`, `listener-controller.ts` and `listener-requests.ts` (part 9a, the listener in the main process): `<app data>/remote/listener.json` (mode 0600, as it holds the secret of the host) keeps the device id, which stays the same on every start so a host sees one device, and the `pairing` (host, port, pinned certificate, secret) of the host that approved it; a wrong part drops the pairing, a cut file counts as missing. `createListenerController` runs the flow in one place: `connect` (the first contact, state `confirming` with the code, nothing asked yet), `confirm` (the user saw the same code on both screens; the request goes out pinned to the certificate that gave the code and repeats every second while the host says `pending`, for at most ten minutes, the time the host keeps it), then `listening`, which keeps `GET /remote/events` open (`followNowPlaying`, the server-sent events of the host; each change arrives at once, no polling) and keeps the last track when one poll fails (with `error`). A 401 ends in `revoked` and forgets the pairing; `blocked`, an approval whose secret was picked up before (the host must revoke it first) and any other answer end in `error` or `blocked` with the reason. `start` follows the saved host, `leave` forgets it, and every connect, confirm and leave takes a new run number, so the loop of an older one ends at its next wake up. The channels: `GET_REMOTE_LISTENER`, `CONNECT_REMOTE_HOST` (`host`, `port` from 1024), `CONFIRM_REMOTE_HOST` (`note` up to 200 characters) and `LEAVE_REMOTE_HOST` from the page, `REMOTE_LISTENER_STATE` (`shared/schemas/remote-listener.ts`) back. The snapshot schema moved to `shared/schemas/now-playing.ts`. The screen, the player that follows the snapshot and the audio relay are the next pull requests. Polling is used and not the `events` stream, as it is one request a second on a LAN; the stream is for a later change if the delay matters.
- The screen to pair (part 9b): `REMOTE_LISTENER_STATE` is read through `shared/schemas/remote-listener.ts` into `uiState.remoteListener` (`undefined` until the main process answers `GET_REMOTE_LISTENER`, sent when the page starts), and `CONNECT_REMOTE_HOST`, `CONFIRM_REMOTE_HOST` and `LEAVE_REMOTE_HOST` actions go to the main process. `pages/remote-listener/RemoteListener.tsx` is the Nearby Tunelles source of the sidebar, next to Radio (part 22; it was a tile of the settings before) and follows the status: the address and port form (also after an error, a block or a revoke, with the reason, and the last address filled in), the code of the host to compare with the one the host shows and an optional note, then the wait for the approval, then what the host plays (title and artist as text, or that nothing plays) with a button to stop. Nothing is sent to the host before the user pressed that the codes match. The host tile shows its port while it listens, as the listener needs it and no discovery exists yet (the address is the one of the computer on the network; mDNS replaces typing both). The player does not follow the snapshot yet, so a listener sees the title and does not hear it.
- The audio of the host (part 9c, main process): `GET tunelle://app/remote/audio` is relayed to `GET /remote/audio` of the host that this app is listening to. The page names neither host nor file: `createListenerController` keeps the host it follows (`audio`), and `remote-media.ts` is the one place the protocol asks (`provideRemoteAudio` from `register-remote-listeners.ts`, `serveRemoteAudio` in `tunelle-protocol.ts`), so a request without an approved host is a 404. `fetchAudio` (pinned, the `Range` of the request goes on, the answer is a stream with status, `Content-Type`, `Content-Length`, `Content-Range` and `Accept-Ranges`) times out only while it waits for the answer: a player that stops reading a buffered stream must not lose it to the idle timeout of the socket (symptom if it did: the audio of a paused listener ends after 5 s). A host that cannot be reached is a 502. Clocks: the snapshot carries the time of the host's clock, so the poll route sends `x-tunelle-time` (its clock when it answered) and `followNowPlaying` moves `at` onto the clock of the listener by the difference taken once, from the `x-tunelle-time` header of the stream when it opens; without it a listener whose clock is seconds off seeks to the wrong place. `expectedPosition` and `driftCorrection` moved to `shared/utils/remote-position.ts`, as the page needs them and the main process does not.
- Following the host (part 9d, the page): the "Listen along" button of the tile loads a synthetic track (`client/domain/remote-track.ts`) with `PLAY_TRACKS` and `PLAY_TRACK`. Its path is `remote://<key>`, the key made of title, artist, album and duration, so a new track of the host is a new path and the audio loads again; `sourceOf` maps it to `tunelle://app/remote/audio?t=<key>` (the main process ignores `t`, it only keeps the cache apart) and `isFileTrack` is false for it, so there is no loudness and no gapless preload. There is no mode in `uiState`: the follow mode is that the loaded track has this path, so starting any other track leaves it by itself. `useRemoteFollow` (in `PlayerControls`, beside `useRemoteHost`) runs on each snapshot of the stream: a track that is not the loaded one is loaded, play and pause follow the state, and `driftCorrection` seeks when the listener is more than 0.5 s off. The track is not recorded in the history, and `useRemoteHost` sends no path for it, as the path of a file never leaves its host. Not checked on two real computers: the audio that starts from the beginning and is then sought to the host's position (symptom if it is wrong: a jump a second after each track change).
- Discovery on the network (part 10a, main process): `electron/remote/mdns.ts` is the `dgram` code and `dns-packet.ts` its wire format. `advertise` (the host) opens one socket for each interface that is up and not loopback, bound to 5353 with `reuseAddr`, joined to `224.0.0.251` on that interface and sending out of it (a reply out of the wrong interface, VPN or docker, reaches nobody); with only loopback up it uses one socket on the default interface. It announces at the start and a second later, answers a PTR or ANY question for `_tunelle._tcp.local`, refreshes at 80 % of the ttl (120 s) and sends the goodbye (a ttl of 0) before it closes. The instance is `tunelle-<code>._tunelle._tcp.local`, with the code of the certificate so two hosts called the same do not collide; the TXT is `name`, `version`, `port` and `approval=request`, nothing of the library or of what plays. The host controller announces after the server listens and not for a host on loopback; a failed announcement is logged and the host keeps working at its address. `browse` (the listener, `nearby.ts`, `BROWSE_REMOTE_NEARBY` and `REMOTE_NEARBY`) asks at once, then after 1 s and then twice as late each time up to a minute, and keeps the records in a cache (at most 256, a goodbye removes at once, the rest leave when the ttl ends, checked every 10 s); a host is in the list when a PTR, an SRV and an A record agree, and the list is sent only when it changes. The socket of the listener is open only while the page shows the list. Tried on Fedora without avahi: one process that advertises and browses finds itself and loses itself at the goodbye. Still **unverified**: two machines, a run next to avahi, the prompts of macOS and Windows, an MSIX package. Not yet: AAAA records, known-answer suppression.
- The list on the page (part 10b): while the connect form of the listener tile is shown (status idle, contacting, error, blocked or revoked) the tile sends `BROWSE_REMOTE_NEARBY` with `active: true`, and with `false` when the form goes away (a pairing, a listening app or another page), so the socket is open only then. `REMOTE_NEARBY` is read through `shared/schemas/remote-nearby.ts` into `uiState.remoteNearby`. A button for a host starts the same request as the typed address (`CONNECT_REMOTE_HOST`), so the host still shows the code to compare before anything is sent; the name comes from the network and is shown as text only, the address is its tooltip. Other languages show the English text for the three new `remote.listen.nearby*` and `connectTo` keys.
- Filters and status of the list (part 11): `browse` leaves out a host that advertises another `protocol` or none (it cannot be listened to; the app version is not the test, as a new release stays compatible until the protocol changes) and the host of this app, which `createNearby` finds through the id the host controller advertises (`advertisementId`, the approval code without separators), asked at each change so it also holds when host mode is turned on while the list is open. The listener tile now keeps the list while it waits or listens (it looked only while the form was shown), shows each host as `Not paired`, `Waiting for approval`, `Approved` or `Blocked` by comparing its address with the host the app talks to, disables the button of a host that waits or is approved, and has `Look again`, which closes the socket and opens a new one so the first question goes out at once. A host that disappears leaves the list when its records end (the ttl, 120 s) or at its goodbye. The entry in the online sources is still open: the list stays in the settings tile.
